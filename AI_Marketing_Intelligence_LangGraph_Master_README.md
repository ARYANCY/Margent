# 1. Product Definition

## Problem

Marketing teams have campaign data across multiple channels and dashboards. It is difficult to determine:

- what is working;
- which campaigns are underperforming;
- which trends are relevant;
- why performance changed;
- which audiences are responding;
- where the next marketing effort should go.

## Product

Build an AI Marketing Intelligence platform that:

1. imports campaign data;
2. obtains legitimate trend signals;
3. normalizes and scores trends;
4. uses an 80/20 exploration/exploitation policy;
5. runs 100 simulated marketing/customer agents;
6. orchestrates agent workflows with LangGraph;
7. uses Grok for reasoning and structured decisions;
8. aggregates all important evidence in one Admin Intelligence Agent;
9. streams state and events to a node-based UI;
10. produces evidence-backed recommendations.

## Important distinction

The 100 agents are **simulated agents**.

Their comments, likes, reactions and engagement are generated by the simulation and must be labelled as simulated/AI-generated. They must not be represented as genuine human engagement.

Real trend data is an external signal; simulated interactions are not real-world measurements.

# 2. What LangGraph Does

LangGraph is a low-level orchestration/runtime framework for long-running, stateful agents. It models workflows using:

- State
- Nodes
- Edges

It supports durable execution, streaming, persistence, human-in-the-loop workflows and fault recovery.

Official JavaScript documentation:
https://docs.langchain.com/oss/javascript/langgraph/overview

For this project, LangGraph is the **agent orchestration layer**.

It is NOT the visualization layer.

It is NOT the campaign analytics engine.

It is NOT the database.

It is NOT the source of trend data.

The separation should be:

```text
LangGraph
    =
Agent orchestration

Python analytics
    =
Numerical/statistical/ML analysis

Grok
    =
LLM reasoning

MongoDB
    =
Persistence

Socket.IO
    =
Real-time transport

React Flow
    =
Visual agent graph
```

LangGraph's Graph API explicitly represents state, nodes and edges and supports loops/conditional execution. It also executes graph work in super-steps, which is useful for the simulation's tick-based design.

Example:


Do NOT assume the React Flow graph and LangGraph graph must have exactly the same topology.

This distinction is important.

# 8. LangGraph Design

## 8.1 Recommended design

Do NOT create 101 completely independent LLM graphs.

That would create unnecessary complexity and API cost.

Instead use:

```text
ONE SIMULATION GRAPH
        │
        ├── Agent Registry
        │
        ├── Shared Simulation State
        │
        ├── Agent Execution Nodes
        │
        ├── Routing Logic
        │
        ├── Event Aggregation
        │
        └── Admin Node
```

Agent identity is data.

Agent behavior is implemented by role-specific functions.

Example:

```text
customer_023
     │
     ▼
customerNode(state, agentId="customer_023")
```

and:

```text
customer_024
     │
     ▼
customerNode(state, agentId="customer_024")
```

The same node function can execute different agent profiles.

# 9. Simulation vs LangGraph

This is the most important architectural decision.

## Simulation engine

Controls:

```text
time
ticks
randomness
agent activation
campaign exposure
probabilities
event generation
```

## LangGraph

Controls:

```text
agent reasoning
state transitions
tool usage
conditional workflows
LLM calls
admin analysis
checkpointing
recovery
```

Therefore:

```text
Simulation Tick
      ↓
Select active agents
      ↓
Invoke LangGraph workflow
      ↓
Agents reason/act
      ↓
Events
      ↓
Analytics
      ↓
Admin
```

Do not force every simulation tick through an LLM.

# 12. Canonical Campaign Schema

Normalize all campaign datasets to:

```text
campaign_id
campaign_name
channel
audience
date
spend
impressions
clicks
conversions
revenue
engagements
```

Derived fields:

```text
ctr
cpc
conversion_rate
roas
engagement_rate
```

Formulas:

```text
CTR = clicks / impressions

CPC = spend / clicks

Conversion Rate = conversions / clicks

ROAS = revenue / spend

Engagement Rate = engagements / impressions
```

Protect against division by zero.

```text
      │
```


so the rest of the system does not depend directly on provider-specific code.



# 21. Trend Score

Start with:

```text
Trend Score =
    0.30 × Growth
  + 0.20 × Interest
  + 0.15 × Velocity
  + 0.15 × Recency
  + 0.20 × Relevance
```

Every component should be normalized to:

```text
0–100
```

Make weights configurable:

```json
{
  "growth": 0.30,
  "interest": 0.20,
  "velocity": 0.15,
  "recency": 0.15,
  "relevance": 0.20
}
```

These weights are a product heuristic, not a scientific universal.

Validate them against historical/simulation results rather than claiming that the formula is objectively optimal.

# 26. Parallel Agent Execution

LangGraph supports graph execution with nodes that can operate in parallel super-steps.

Use parallelism carefully.

Do not invoke 100 LLM calls simultaneously.

Instead:

```text
100 registered agents
       │
       ▼
active-agent selector
       │
       ▼
5–20 active agents
       │
       ▼
parallel execution
```

The exact concurrency limit should be configurable.

Example:

```env
MAX_ACTIVE_AGENTS_PER_TICK=15
MAX_LLM_CONCURRENCY=5
```

# 36. Admin Output Schema

```ts
const AdminAnalysisSchema = z.object({
  priority: z.enum(["LOW", "MEDIUM", "HIGH", "CRITICAL"]),

  decision: z.enum([
    "SCALE",
    "MAINTAIN",
    "INVESTIGATE",
    "EXPERIMENT",
    "REDUCE",
    "STOP"
  ]),

  summary: z.string(),

  evidence: z.array(z.string()),

  recommendedActions: z.array(z.string()),

  confidence: z.number().min(0).max(1),

  exploitationAllocation: z.number().min(0).max(1),

  explorationAllocation: z.number().min(0).max(1)
});
```

Validate the response before writing it to the database.

# 103. Final Recommendation

Use this architecture:

```text
                  LANGGRAPH
                     │
       ┌─────────────┼─────────────┐
       │             │             │
   Agent Flow    State/Memory   Routing
       │             │             │
       └─────────────┼─────────────┘
                     │
                    GROK
                     │
               Reasoning only
                     │
                     ▼
              ADMIN INTELLIGENCE
                     │
        ┌────────────┼────────────┐
        │            │            │
       ML        Analytics      Trends
        │            │            │
        └────────────┼────────────┘
                     │
                 EVENT BUS
                     │
                 WEBSOCKET
                     │
                     ▼
                REACT FLOW
                     │
                     ▼
                 DASHBOARD
```

The key architectural rule is:

> **LangGraph orchestrates; Grok reasons; Python calculates; MongoDB persists; Socket.IO streams; React Flow visualizes.**

That separation gives the project a much cleaner architecture than trying to make LangGraph itself responsible for the entire application.
